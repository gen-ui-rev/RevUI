# RevUI

RevUI is a dataset of designer assessments of generated UI revisions. Each revision case links a source UI, a revision request containing one to three request units, and two generated revisions (A and B). The release provides revision requests and annotations, HTML files, rendered PNG images, and designer assessments in SQLite and CSV formats.

## Constructing UI revision cases

### Source UIs

The initial generation pool comprised 1,200 source UIs, with 600 assigned to each of two models: **Claude Opus 5** (`anthropic/claude-opus-5`) and **GPT-5.6 Sol** (`openai/gpt-5.6-sol`). Models generated HTML interfaces from prompts specifying the screen category, application context, and visual attributes.

We used a taxonomy adapted from **Mobbin screen categories**, covering 112 categories in ten groups: Account Management, Actions, Commerce & Finance, Communication, Content, Data, New User Experience, Social, User Collections, and Utility. The taxonomy guided the types of interfaces to generate.

Source UIs were distributed approximately equally across categories: 80 categories received 11 source UIs each and 32 received 10 each. Model assignments were balanced within categories. Application domains and visual attributes, including typography, color, and component styling, were also varied through a balanced allocation. The pool included both full-screen interfaces and individual UI components.

### Revision requests

Each source UI received a revision request generated by the model that created it. Generation was organized around **seven change targets and four levels of request specificity**, yielding 28 combinations.

The seven change targets and four levels of request specificity were derived from the findings of our formative study. The names below follow Tables 1 and 2 of the paper.

| Change target | Description |
|---|---|
| Content and information | Add content or make existing information more specific. |
| Function and action | Add controls or actions, such as sorting, filtering, or gestures. |
| Layout and hierarchy | Adjust the placement, size, alignment, or emphasis of existing elements. |
| Flow and information architecture | Change the organization of steps, groups, or information structures. |
| Context and scenario | Adapt the interface to a different service, situation, or intended user. |
| Environment | Adapt the interface to another device or usage environment. |
| Style | Change the visual treatment or overall look and feel. |

| Level | What is specified |
|---|---|
| L1: Solution | The element, its placement, and its form. |
| L2: Element | The element to add or change, leaving its placement or form open. |
| L3: Goal | The desired outcome, leaving the means open. |
| L4: Direction | A direction for change, leaving the desired outcome and solution open. |

Revision requests contained one, two, or three request units, with approximately equal allocations to these three sizes. Change-target–specificity combinations were balanced across the generation pool and within each model. The model first constructed unit-level specifications grounded in the source UI, expressed each unit at its assigned specificity, and combined them into a complete revision request while preserving unit metadata. The revision request was used to generate revisions. Each request unit belongs to one assigned specificity level; the release does not provide four matched versions of the same unit.

### Author review

Three authors reviewed the source UIs and their associated revision requests, dividing the items among themselves. Review considered the usability of the source UI as an evaluation stimulus, the coherence of the requested changes, and their consistency with the assigned target and specificity level. This review informed the selection of examples used in the study.

### Generated revisions

Claude Opus 5 and GPT-5.6 Sol were also used as revision-generating models. Assignments were counterbalanced across source-model provenance, with approximately balanced assignments across the two origins. For each revision case, one model received the source HTML and complete revision request and generated A and B in a single call. The prompt asked for distinct approaches to addressing the same request. A and B are therefore paired responses to a shared revision problem rather than independently sampled outputs.

The released 1,000 revision cases comprise 499 revision pairs generated by Claude Opus 5 and 501 by GPT-5.6 Sol. A and B identify the two revisions generated by the same model for a case; they do not identify different models.

## Generation prompts

The [prompt documentation](prompt/README.md) describes the generation flow and how to assemble the released templates. Related rules are grouped into six TXT files across three directories:

| Directory | Contents |
|---|---|
| [Source UI generation](prompt/source-ui-generation/generation.txt) | Source UI generation, canvas and visual options, and validation-repair messages. |
| [Revision request generation](prompt/instruction/) | Applicable change targets, unit-level specifications, request units, and complete revision request assembly. |
| [Revision generation](prompt/alternatives/generation.txt) | Joint A/B generation and canvas options. |

These templates are edited for the public release rather than verbatim API request logs. Named placeholders represent the inputs supplied for each revision case.

## Release contents

The initial generation allocation described above is distinct from the final release, which contains:

| Item | Count |
|---|---:|
| Revision cases | 1,000 |
| Generated revisions | 2,000 |
| Distinct request units | 1,971 |
| Evaluation submissions | 1,600 |
| Region annotations | 2,613 |
| Train / validation / test cases | 700 / 100 / 200 |

The released revision requests contain one request unit in 346 cases, two in 337, and three in 317. All 28 change-target–specificity combinations are represented. The initial balanced generation design does not imply exact balance in the final release.

`RevUI.db` contains the following tables. Each table is also available as `csv/<table>.csv` with the same column names and rows:

| Table | Contents |
|---|---|
| `sets` | Case split, category, source-model provenance, and request summary metadata. |
| `requests` | Complete revision request and source UI viewport dimensions. |
| `revisions` | Revision-generating model, declared viewport dimensions, interactivity, and device metadata for A and B. |
| `units` | Request units, change targets, and specificity levels. |
| `evaluations` | Evaluation submission identifiers, pseudonymous designer codes, comparative preferences, and written explanations. |
| `unit_scores` | Request-unit–revision assessments and shared explanations for the three request-related ratings. |
| `revision_items` | Revision-level assessments of unrequested changes, design-quality changes, and overall quality, with explanations. |
| `regions` | Region annotations and spatially anchored explanations. |
| `labels` | Aggregated comparative preference labels for validation and test cases. |

A `set_id` identifies a revision case, and `revision` identifies revision A or B. The `requests` table stores the revision request, while `revisions` stores metadata for the generated revisions.

The stored `units.target_name` values map to the paper's change targets as follows:

| Stored value | Paper term |
|---|---|
| `Content & Information` | Content and information |
| `Functionality & Behavior` | Function and action |
| `Layout & Hierarchy` | Layout and hierarchy |
| `Flow & Information Architecture` | Flow and information architecture |
| `Situation, Context & Scenario` | Context and scenario |
| `Environment` | Environment |
| `Style` | Style |

CSV files use UTF-8 with a byte order mark (BOM) and include a header row. Fields containing commas, quotes, or line breaks are CSV-quoted. SQL `NULL` values are exported as empty fields, so CSV does not distinguish them from empty strings. Use the SQLite database when SQL types, constraints, or this distinction are needed.

Join case-level records using `set_id`. Join `unit_scores`, `revision_items`, and `regions` to `evaluations` using `submission_id`. Request units are identified by `(set_id, unit_ordinal)`. The `sets.model` aliases `opus` and `sol` refer to the **model that generated the source UI and revision request**; the revision-generating model is recorded in `revisions.model` as a full model identifier. Join `revisions` using `(set_id, revision)`. `viewport_w` and `viewport_h` are declared CSS-pixel dimensions; `interactive` is 0 or 1, and `device` is the device label when specified.

The 1,000 released revision cases are numbered consecutively from `inst-0001` to `inst-1000`, following the original numeric order. Database case identifiers (`set_id`) and HTML/PNG filenames use the same numbering. Evaluation submission identifiers are retained to preserve annotation joins.

For `inst-0001`, the files are:

```text
html/original/sample-0001.html
html/revisions/inst-0001_a.html
html/revisions/inst-0001_b.html
img/original/sample-0001.png
img/revisions/inst-0001_a.png
img/revisions/inst-0001_b.png
```

The release contains 3,000 HTML files and 3,000 PNGs: one source UI and two revisions per case. Only cases present in the database are included. Metadata is available in the database and CSV files, so separate JSON sidecars are unnecessary. `requests.original_w` and `original_h` describe the source UI; `revisions.viewport_w` and `viewport_h` describe each revision's declared viewport. Read each PNG's actual dimensions for bounding-box overlays.

The publication files are `README.md`, `RevUI.db`, `csv/`, `html/`, `img/`, and `prompt/`. Local backups and audit working files are outside the release contents.

## Bounding boxes

`regions.revision` identifies A or B. Its `x`, `y`, `w`, and `h` fields represent normalized left, top, width, and height, with a top-left origin. For the matching PNG of pixel size `W × H`, draw an approximate overlay as follows:

```python
left = x * W
top = y * H
right = (x + w) * W
bottom = (y + h) * H
```

Coordinates were collected relative to the evaluation frame. The supplied PNGs serve as the fixed visual reference for approximate overlays. During release preparation, 37 boxes extending slightly beyond the frame were clipped to the normalized unit rectangle, preserving their visible positions. Other coordinates were retained.

HTML rendering can differ with viewport size, fonts, and cropping, so boxes should not be assumed to align with an arbitrary re-rendering. Evaluation HTML had external stylesheet links removed, which can also affect typography relative to the separately distributed HTML. Historical per-evaluation frame heights are not included; exact alignment across all HTML renderings and PNGs is therefore not guaranteed. The bounding-box cleanup corrects frame-boundary overflow, not layout or crop differences.

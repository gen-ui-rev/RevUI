Instruction generation: individual requests
===========================================

SYSTEM
------
You turn a UI change spec into the sentence a designer would actually type.
Write one revision request in English.

{level_rules}
{target_rules}

Rules:
- Never restore information the assigned level told you to drop.
- Write a plain imperative request ("Add ...", "Make ...").
- Stay inside the length target. Being under it is fine; going over is not. If it runs
  long, drop a word — never drop information the level is supposed to keep.
- Quote on-screen copy in English.
- No preamble, no explanation.

Output: JSON and nothing else.
{"en": "..."}

LEVEL RULES: insert as {level_rules}
------------------------------------
Four instruction levels. Each fixes part of the change and leaves the rest open.
Say only what its line fixes.

L1 the solution : element, position, and form.
L2 the element  : what to touch and what to do. Position and form stay open.
L3 the goal     : the end state. The element and the means stay open.
L4 a direction : what changes, and that it should differ. Never what it becomes.

Name the element as it looks on screen. At L4, keep that name only if `element` is one
part of the screen; if it is the whole screen, the axis alone is the request.
Say the axis the way someone would say it pointing at the screen, rather than using
a design-taxonomy term. Still never say what it becomes.

The request must still read as the kind of change it is. "Add a way to save this" and
"Rearrange this" are different requests even when they touch the same card. If the
axis is so broad that both would fit, the sentence has lost the request. Say the
kind of change plainly, and stop before saying what the result becomes.

TARGET RULES: target F, at every level
--------------------------------------
This request changes the device. The device name is the situation the request lives in,
not the means — so it survives every level, L4 included. Name the device in the request:
tablet, desktop, or smartwatch. At L4 the request is the device plus the axis and
nothing more.

What moves is the whole screen, so the object of the sentence is the screen, never a
part of it. Moving one list to another device while the rest stays put is not a
coherent change.

The device is where the screen is going, not where it already is. The change being
requested is the move. Say the move, then what follows from it.

TARGET RULES: target E, at every level
--------------------------------------
This request changes who the screen is for, or what it is about. That swap is the
request — say it, then say what follows from it. A sentence that only describes what
the new audience needs takes the swap as already done and asks for something on top.
The new subject or audience is where the screen is going, not a condition it already
meets.

ADDITIONAL TARGET RULE: target E at L4
--------------------------------------
At L4, the swap is the whole request: say that the audience or the subject changes,
never who or what it becomes.

-----------------------------------

REJECTION REASON: missing device
--------------------------------

Instruction generation: change specification
============================================

SYSTEM
------
You are a research assistant building a dataset of UI modification requests.
You design changes to a screen and write each one as a five-slot spec — not as
a sentence yet.

  element  : which part of the screen is touched.
             Name it the way a designer would point at it: the ordinary name first ("the header", "the chip list"), add
             position or order when several are alike.
  now      : how that part stands right now — including how well it already handles
             the thing you are about to change (short)
  goal     : the end state that differs from now (never the means)
  solution : the settled fix, position and form included (one sentence)
  axis     : what kind of change this is. English, at most three words.
             Two tests, and it has to pass both.
               too broad  — if the same axis would fit a different change type
                            applied to the same element, narrow it
               too much   — if someone could carry out the change knowing only the
                            axis, it is saying the result. The axis names the kind of
                            change, never what the result becomes.
             Not a design-taxonomy word.

This is what a designer would say while designing the app while reworking this screen —
not a developer. About the screen, not writing the code. Never write:
- CSS selectors or class names (`.section-header`, `#hero`) — name the part the way a
  designer would say it out loud (the header, the list, the bottom button), and
  quote on-screen copy only when the name alone would be ambiguous
- CSS properties or values (`flex-direction: row`, `margin-bottom`, `display:none`)
- px, hex, or rgba numbers (`28px`, `#636366`) — say "a bit bigger", "half the size",
  "dark gray", "side by side", "stacked"
- copy, addresses, amounts, or counts that are not on the screen ("88 Adler St",
  "$84,200", "12 places") — name the kind of information instead ("one line of address").
- Avoid copying the contents. Instead, refer to the type or position of content ("the first card", "the top button", "the cancel button", "the three plans").
  If you must quote, it is because of ambiguity or complexity, nothing else.

Constraints:
- Never ask for the screen to be operated (turn a switch on, pick an item). The result
  is a still screen, so nothing would change. B grants an action that does not exist
  yet; it does not use one that does.
- Do not touch an element that is not in the HTML (A is the exception — it adds content)
- Do not do another change type's job. A layout change (C) must not add a button.
- Keep it to what fits one screen. The source UI is a fixed size, so anything you add must
  be small enough that something else can come out.
- goal must differ from now, and avoid to change something the screen already does
  well. If the element already reads clearly, is already prominent, is already grouped
  sensibly — pick a different element or a different angle. But it is OK to say "make it more prominent" if it is already prominent but not enough, or "make it clearer"
- solution is one sentence and touches one place. Even when the whole subject changes
  (E), do not enumerate — say "X becomes Y" plus the one item that becomes necessary
  or unnecessary because of it.
- Name colors plainly or point at a color already on the screen.

CONDITIONAL SYSTEM RULES: append when the instruction contains two or three requests
------------------------------------------------------------------------------------
Designing a set
One person asks for all of these in one breath, so they have to hold together as one
reworking of the screen — not separate ideas that happen to share a source UI.

Order them yourself. Read the change-type definitions and see how much of the screen
each one redefines: changing what the screen is about, or what device it lives on,
resets everything after it; rearranging or recolouring one part resets nothing.
Say the one that redefines the most first, then narrow down — unless that order is not what a
person would actually say, in which case say it the way they would.

Then design them in that same order:
- the first spec is the ground; every later spec must be true of the screen AS THE
  EARLIER SPECS LEAVE IT, and must not point at copy or a part that an earlier spec
  removes or replaces
- no two specs may name the same `element`
- each spec must still be satisfiable, and judged, on its own — if satisfying an
  earlier one would make a later one true for free, give the later one a different
  element or angle
- together they must still fit one screen

SYSTEM OUTPUT FORMAT: append after the applicable system rules
--------------------------------------------------------------
Output: JSON and nothing else. One entry per assigned change type, ordered as they
should be said, each echoing the letter and the sid it answers.
{"specs": [{"target": "<letter>", "sid": "<sid>", "element": "...", "now": "...",
            "goal": "...", "solution": "...", "axis": "..."}]}

CONDITIONAL USER RULE: insert as {device_rule} when target F is assigned
------------------------------------------------------------------------
Name the target device in `solution`, exactly one of: tablet / desktop / smartwatch. No pixel sizes.
For this change type `element` is THE WHOLE SCREEN, never a part of it — moving to another device moves everything. Write it as the screen itself ("the screen", "the whole booking screen"). An element like "the result list" would ask for one list to become desktop while the rest stays, which is not a thing anyone can do.
